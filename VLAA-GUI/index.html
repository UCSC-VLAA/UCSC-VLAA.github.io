01 Overview

GUI agents stop too early, and they get stuck in loops

Desktop agents built on multimodal LLMs can now click, type, and scroll through real applications. Two failure modes still decide most outcomes. Existing planners track generated subtasks, but finishing the planned steps does not mean the user’s requirement is met. Existing anti-loop heuristics catch local repetition, but have no way to escalate when the agent stays stuck.

Early stopping

The agent declares success without verifiable evidence: it toggles a setting without checking that the state changed, or edits a file and never saves it. Completion is left to the model’s implicit judgment instead of being checked against what the UI shows.

95.5%of Sonnet 4.6’s failed OSWorld tasks end with a false done() when the Completeness-Aware Planner is removed (100 steps)

Repetitive loops

The agent repeats the same failing action, or cycles through the same screens, and burns its step budget without progress. Detecting the repetition is not enough; the agent has to be pushed onto a different interaction mode or strategy.

20.7%of Gemini 3 Flash’s failed tasks involve loops without the Loop Breaker, and 4.9% of all its steps are spent inside them

02 Abstract

Autonomous GUI agents face two fundamental challenges: early stopping, where agents prematurely declare success without verifiable evidence, and repetitive loops, where agents cycle through the same failing actions without recovery. Existing agent planners track progress through generated subtasks, yet in GUI environments, completing planned steps does not guarantee that the user’s requirements are met. Moreover, existing anti-loop mechanisms typically detect only local repetition and lack mechanisms to escalate recovery when the agent remains stuck. To this end, we present VLAA-GUI, a modular GUI agentic framework organized around three decisions: when to Stop, Recover, and Search. To prevent premature termination, a mandatory Completeness-Aware Planner tracks UI-observable success criteria throughout execution and independently verifies completion claims before termination. To recover from stalled agent action loops, a mandatory Loop Breaker detects repeated ineffective agent actions and progressively forces the agent to change its action strategy. When the current observation is insufficient to determine a viable workflow, an on-demand Search Agent supplies external procedural knowledge to the agent.

To validate VLAA-GUI, we evaluate it on two benchmarks containing Linux and Windows tasks with five LLM backbones, achieving top performance on both (77.5% on OSWorld and 61.0% on WindowsAgentArena). Notably, three of the five backbones surpass human performance (72.4%) on OSWorld in a single pass. Ablation studies further show that completion checking, loop recovery, and search provide complementary gains that vary with backbone capability and interaction budget, while the Loop Breaker nearly halves wasted steps for loop-prone backbones (e.g., Gemini 3 Flash). Moreover, transferring three proposed mechanisms to an existing GUI agent (CoAct-1) also improves it by over 5% to 70.3% on a controlled OSWorld subset, showing the strong portability of these components.

03 Method

One Manager, two mandatory checks, three on-demand tools

VLAA-GUI is built around a single Manager agent that perceives, reasons, and acts on the GUI in one loop. At step t, its belief state bt summarizes the instruction, the trajectory so far, and the current screenshot and tool results. From it, the Manager picks one action: a UI primitive (click, type, scroll, hotkey) or a call to the Search, Coding, or Grounding Agent. All of these share one action space, so the Manager chooses the help that fits the obstacle in front of it and stays responsible for the task throughout.

STOPMandatory

Completeness-Aware Planner

Conventional hierarchical planners decompose how to execute a task, and give weak signals about whether the requested outcome was reached. The Completeness-Aware Planner (CAP) instead represents what must be true for the task to be complete.

Completion Gate. From the instruction, the Manager derives K UI-observable success criteria (1–3 in practice; exact values such as a hex color are tagged for a literal check). The criteria prescribe no action order, so the Manager can change its route without losing track of what it must finally demonstrate. Each step it re-checks every criterion against the screen, and action-specific rules tell it what visible outcome to expect, so a UI that has not updated yet is not mistaken for success.

Completeness Model Judge. The gate only conditions on the initial instruction, so it can miss requirements. When it outputs DONE, a separate MLLM judge (temperature 0.2) re-reads the instruction with the current screenshot and recent trajectory. It accepts only with direct visual evidence for every criterion, visible confirmation of side effects such as saving, exporting, or sending, and a stable UI. The agent terminates only when gate and judge agree; a rejection appends criterion-level evidence and what is still missing to the trajectory.

Every step
  1. 1
    Write success criteria
    At the first step, 1–3 statements the screen can confirm: button labels, file names, toggle states, dialog titles.
  2. 2
    Check them against the screen
    Each criterion’s evidence is updated from what is visible now.
    Gate(bt) = DONE if all K criteria pass and the UI is stable, else CONTINUE
  3. 3
    Independent judge on every done()
    RejectMissing evidence goes back into the trajectory; the Manager keeps working.
    AcceptGate and judge agree: the task ends with agent.done().
RECOVERMandatory

Loop Breaker

Repeated failure can come from an ineffective interaction, an unproductive workflow, or a broader pattern in the trajectory. The Loop Breaker runs after every Manager action and handles all three. Tiers 1 and 2 count repeated actions that leave the screen unchanged and recurring screen states; Tier 3 asks an external model to read the recent trajectory.

The thresholds are fixed, τa = 2 and τo = 3, across all tasks and both benchmark platforms. Repetition alone never establishes that a task is infeasible; declaring failure needs separate evidence.

Escalation
  1. TIER1
    Modality switch
    same action, no visible change, twice (na ≥ 2)
    The next action must use another modality: keyboard shortcut → menu click → command line.
  2. TIER2
    Strategy change
    same screen state three times (no ≥ 3)
    The overall strategy must change, e.g. from menu navigation to programmatic file editing.
  3. TIER3
    Reflection-driven judge
    external model returns KEEP or SWITCH
    On SWITCH, the repeated action is blacklisted for the next step: click → type, or GUI actions → the Coding Agent.
SEARCHOn demand

Search Agent

Recovery can change the route, but in an unfamiliar application the agent may have no good alternative to try. The screen shows the interface; it rarely shows the procedure. A short tutorial supplies the missing workflow.

Retrieving it through a visual browser, as in OS-Symphony, adds navigation and grounding of its own. Because the knowledge sought is procedural text, VLAA-GUI asks for text directly: the Manager calls search(query) from the same action space as UI primitives, with a targeted “How to” question. An LLM with native search grounding (Gemini 3 Pro or 3.1 Pro) answers in a single query with a summarized tutorial, which joins the belief state. The Manager calls it when it is unsure of a GUI workflow and a tutorial is likely to exist.

Coding Agent

Runs Python and Bash in its own loop, with an independent budget of 20 code-execution steps. The Manager calls it for bulk edits (20 or more cells or lines), non-trivial computation, or when the GUI route is blocked.

Grounding Agent

Turns a natural-language element description into screen coordinates on the 1920×1080 screenshot. Seed 1.8 by default; one Opus 4.5 configuration uses MAI-UI instead.

For Sonnet 4.6 at 100 steps, removing CAP costs 2.86 points, removing search 1.63, and removing loop control only 0.04. For Gemini 3 Flash, loop control adds 4.24 points at 50 steps and search 2.95 at 100 steps.

Verification is not uniformly beneficial: at 50 steps Gemini 3 Flash scores 66.00% without CAP and 63.14% with it. At 100 steps the sign flips (68.77% with, 67.34% without).

On WindowsAgentArena the effects are larger. Removing search, CAP, or the Loop Breaker lowers the 50-step score by 11.0, 9.1, and 7.8 points, and the 100-step score by 7.1, 9.7, and 5.2. Without CAP, Office accuracy falls from 32.6% to 11.6% at 50 steps.

CAP cuts false completions; the Loop Breaker cuts wasted steps

False completions, with CAP

  • Sonnet 4.6, false done() count 105→91
  • Sonnet 4.6, false DONE among failed tasks 95.5%→91.9%
  • Gemini 3 Flash, false DONE among failed tasks 91.9%→86.2%

Even with CAP, more than 86% of failed tasks still end with an incorrect completion claim for both backbones. CAP only partially resolves false completion, which remains the dominant failure mode.

Loops, with the Loop Breaker

  • Gemini 3 Flash, failed tasks involving loops 20.7%→16.2%
  • Gemini 3 Flash, steps wasted in loops 4.9%→2.8%
  • Sonnet 4.6, steps wasted in loops 3.2%→2.1%

Gemini 3 Flash loops roughly twice as often as Sonnet 4.6 (10.6% vs. 5.0% of all tasks), so the weaker, loop-prone backbone gains more from explicit loop recovery.

Tools cost actions, so tight budgets change the picture

Every tool call spends an action. Sonnet 4.6 is step-efficient enough to absorb that overhead and gains from CAP and search at every budget (CAP: +2.5 points at 15 steps, +2.9 at 100). Gemini 3 Flash needs more raw actions per task, so at 15 steps the overhead crowds out execution (CAP −11.3, search −9.7), while at 100 steps both help.

06 Case study

Two rejected done() calls and one search

An OSWorld task in LibreOffice Impress: change the color of the slide number to red. The Manager fails twice before it finishes, and each failure is caught before it would have been scored.

  1. 1

    First attempt

    The Manager edits one master slide and calls done().

    CAP rejects: slide number still gray, file not saved
  2. 2

    Search

    Prompted by the rejection, the Manager calls the Searcher. The tutorial contains the key line:

    “If your presentation uses different master slides for different sections, repeat for each master slide.”

    Finds a second master named OBJECT it had overlooked
  3. 3

    Second attempt

    It applies the color change to both masters and calls done() again.

    CAP rejects: color correct, file still unsaved
  4. 4

    Save and finish

    After an explicit Ctrl+S, the judge accepts the result.

    CAP accepts

CAP prevents early termination while the Searcher supplies task-specific knowledge. Without CAP, the first done() would have ended the run on an unfinished task.

07 Limitations and outlook

What VLAA-GUI does not solve yet

Proprietary models

Every evaluated Manager backbone is proprietary, and the controlled studies also use proprietary Coder and Searcher models, so generality to open models is not established. Model-version changes, API availability, and changing search results limit exact reproducibility.

Scope of the controlled studies

The 60-task subset is fixed and non-random, so it gives controlled point estimates rather than population-level or statistically significant claims. The loop thresholds are hand-designed and have not been swept.

Next: memory and context management

The Manager works from the instruction, the trajectory history, and the current observation, and nothing carries over between tasks. More sophisticated memory and context management may further improve performance on long, multi-step tasks.
